# Cursor 实现指南

## 1. Cursor Agent 机制简介

Cursor 通过 **`.cursor/rules/`** 目录下的规则文件来定义 Agent 行为。规则文件使用 Markdown 格式，通过文件头部的 `frontmatter` 元数据声明触发条件和行为描述。

### 规则文件结构

```
.cursor/
└── rules/
    ├── architect.mdc        # 架构师规则
    └── coder.mdc            # 执行者规则
```

每个 `.mdc` 文件包含：
- **frontmatter**: 描述规则名称、文件模式匹配、触发方式
- **正文**: 使用自然语言描述 Agent 的行为指令

### 触发方式

Cursor 支持两种触发模式：

| 模式 | 描述 | 适用场景 |
|------|------|----------|
| **自动 (always)** | 文件匹配时自动附加到对话上下文 | 全局行为约束 |
| **手动 (manual)** | 通过 `@Rule` 手动引用 | 按需激活特定角色 |

> **关键限制**: Cursor **不支持 Agent 间自动调用**。即一个 Agent 不能自动将任务转交给另一个 Agent。这与 OpenCode 的 `--goals` 传递或 Claude Code 的 `/coordinator` 有本质区别。

## 2. Architect 规则示例

文件: `.cursor/rules/architect.mdc`

```markdown
---
description: Architect - 系统架构师，负责需求分析、架构设计、任务拆解
globs: *
alwaysApply: true
---

# Architect（架构师）

你是 Thinker+Executor 模式中的 **Thinker**。你的职责是分析、设计、规划，**不写代码**。

## 核心工作流

1. **接收需求** — 理解用户要什么
2. **分析现状** — 阅读相关代码，理解当前架构
3. **设计方案** — 输出架构方案，包括：
   - 实现思路
   - 文件结构变化
   - 核心逻辑变更
   - 边界情况与风险
4. **拆解任务** — 将方案拆解为可执行的**任务包**
5. **交付任务包** — 每个任务包遵循以下格式：

```markdown
## 任务包

### 定位
- **目标文件**: [文件路径]
- **修改区域**: [具体位置]
- **上下文**: [背景说明]

### 分析
- **现状**: [当前状态]
- **约束**: [限制条件]

### 目标
- **期望结果**: [具体描述]
- **验收标准**: [检查清单]
```

## 关键原则

- **你不写代码** — 分析、设计、规划是你的全部工作
- **任务包是输出** — 每个任务必须精确到文件路径和修改区域
- **诚实评估** — 不确定时明确说不确定
- **一个任务包只做一件事** — 保持原子性
```

## 3. Coder 规则示例

文件: `.cursor/rules/coder.mdc`

```markdown
---
description: Coder - 执行者，负责按任务包实现代码
globs: *
alwaysApply: true
---

# Coder（执行者）

你是 Thinker+Executor 模式中的 **Executor**。你的职责是精确执行任务包，**不思考设计**。

## 核心工作流

```
收到任务包
    ↓
[1] 解析任务包 — 理解定位、分析、目标
    ↓
[2] 读取目标文件 — 确认当前状态
    ↓
[3] 执行改动 — 严格按目标执行
    ↓
[4] 验证结果 — 编译/测试/检查
    ↓
[5] 提交 summary — 报告完成情况
```

## Summary 格式

```markdown
## Summary

### 完成内容
- [具体做了什么改动]

### 变更文件
- `文件路径`: [改动说明]

### 验证结果
- [x] 编译通过 / 测试通过 / 手动验证

### 遗留问题
- [如有，没有则写"无"]
```

## 关键原则

- **严格按任务包执行** — 目标是什么就改什么
- **改动范围精确** — 只动任务包指定的文件和区域
- **提交 summary** — 每次执行完必须提交
- **保留原有风格** — 匹配项目现有代码风格
- **不超出范围** — 任务包没说的不要碰
- **不重构** — 不要"顺手"改其他代码
- **不加功能** — 不要加任务包没要求的功能
```

## 4. 当前限制

Cursor 的 Agent 机制在实现 Thinker+Executor 模式时存在以下限制：

| 限制 | 说明 | 影响 |
|------|------|------|
| **无 Agent 间调用** | 无法通过 API 或命令让 Architect Agent 自动调用 Coder Agent | 无法自动化流转 |
| **单 Agent 上下文** | 每个对话只有一个 Agent 角色生效 | 需要手动切换角色 |
| **规则合并** | `alwaysApply: true` 时所有规则都会注入上下文 | 角色指令可能冲突 |
| **无任务队列** | 没有内置的任务包传递机制 | 任务包需要手动复制粘贴 |

### 为什么会有这些限制

Cursor 的 `.cursor/rules/` 设计初衷是**为当前对话提供行为指南**，而不是构建多 Agent 协作系统。它没有类似 Claude Code 的 `/coordinator` 命令或 OpenCode 的 `--goals` 参数传递机制。

## 5. 变通方案

由于 Cursor 不支持 Agent 间自动调用，推荐使用 **手动切换 + 复制粘贴** 的变通方案。

### 工作流程

```
[用户提出需求]
     ↓
① 用户手动切换为 Architect 模式（@Rule 引用 architect.mdc）
     ↓
② Architect 分析并输出任务包
     ↓
③ 用户手动复制任务包内容
     ↓
④ 用户手动切换为 Coder 模式（@Rule 引用 coder.mdc）
     ↓
⑤ 将任务包粘贴到 Coder 对话中
     ↓
⑥ Coder 执行并输出 summary
     ↓
⑦ 回到步骤①（如有下一个任务包）
```

### 操作细节

#### 切换到 Architect

在 Cursor 对话中输入：

```
@Rules architect.mdc
```

或者直接在 `.cursor/rules/architect.mdc` 中设置 `alwaysApply: true`（推荐），这样 Architect 指令始终可用。

#### 切换到 Coder

同样在 Cursor 对话中输入：

```
@Rules coder.mdc
```

> **建议**: 两个规则都设置 `alwaysApply: true`，因为它们描述的是**角色的行为准则**而非特定任务指令。它们共存于上下文中不会有冲突——Architect 部分告诉 Agent "当作为架构师时如何思考"，Coder 部分告诉 Agent "当作为执行者时如何行动"。用户通过**对话中的自然语言**来指定当前角色（例如："你现在是 Architect，请分析..."）。

### 任务包传递格式

任务包以 Markdown 代码块形式传递，Coder 对话中直接粘贴即可：

~~~markdown
## 任务包

### 定位
- **目标文件**: `src/main.c`
- **修改区域**: `uart_init()` 函数
- **上下文**: 需要添加波特率配置

### 分析
- **现状**: 无初始化参数
- **约束**: 必须兼容现有调用方

### 目标
- **期望结果**: 支持 9600/19200/115200 波特率配置
- **验收标准**: 编译通过，串口输出正常
~~~

### 多轮迭代建议

当需要多轮 Architect → Coder 迭代时：

1. **保持 Architect 对话**：让 Architect 在一个对话中完成所有分析，输出一系列任务包
2. **逐个执行**：每次复制一个任务包到新的 Coder 对话中执行
3. **反馈回路**：Coder 执行完毕后，将 summary 反馈给 Architect（复制回 Architect 对话）
4. **下一轮**：Architect 根据 Coder 的反馈调整后续任务包

## 6. 安装步骤

### 步骤一：创建规则目录

```bash
mkdir -p .cursor/rules
```

### 步骤二：创建规则文件

将上述 **Architect 规则示例** 保存为 `.cursor/rules/architect.mdc`，将 **Coder 规则示例** 保存为 `.cursor/rules/coder.mdc`。

### 步骤三：验证规则加载

1. 在 Cursor 中打开项目
2. 在对话中输入 `@Rules`，确认两个规则文件出现在下拉列表中
3. 输入任意内容，观察对话上下文中是否包含规则内容（可通过 Cursor 的上下文面板查看）

### 步骤四：创建实现目录（可选）

```bash
mkdir -p implementations
```

用于存放各平台的实现文档。

## 7. 测试验证

### 验证方法

| 验证项 | 方法 | 预期结果 |
|--------|------|----------|
| 规则文件存在 | 检查 `.cursor/rules/` 目录 | `architect.mdc` 和 `coder.mdc` 均存在 |
| 规则语法正确 | 在 Cursor 中引用 `@Rules` | 规则出现在建议列表中，无解析错误 |
| Architect 行为 | 以 Architect 角色分析一个需求 | 输出为任务包格式，不包含代码 |
| Coder 行为 | 以 Coder 角色执行一个任务包 | 输出为 summary 格式，按包内容改动 |
| 角色切换 | 在同一对话中先后以两种角色工作 | 行为随角色切换而变化 |

### 测试示例

1. **测试 Architect**: "我们现在需要添加一个 LED 闪烁功能。请分析并输出任务包。"
   - 期望输出: 包含目标文件、分析、任务拆解，**不包含直接代码实现**

2. **测试 Coder**: 粘贴上述任务包并执行
   - 期望输出: 实现代码改动，输出 summary

---

## 总结

Cursor 的 Thinker+Executor 模式实现需要**人工介入角色切换**，这是其与 OpenCode、Claude Code 的最大区别。优势在于配置简单（两个 `.mdc` 文件即可），劣势在于无法自动化流转。对于小团队和个人开发者，这种变通方案已经足够高效。
